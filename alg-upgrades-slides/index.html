Algorithm Upgrades

Moving existing credentials to post-quantum algorithms, one sign-in at a time

Nina Satragno · Google

Hi everyone. This is a proposal for upgrading existing WebAuthn credentials to new algorithms, especially post-quantum ones, during a normal sign-in. It's a simpler alternative to Akshay's algPolicy explainer.

Motivation

Why now

Keep this short: the WG knows the PQC story.

Scope

Goals & non-goals

Goals

  • Upgrade users to a new algorithm during a get()
  • No lock-out if the response never reaches the RP
  • Extensions keep working after the migration
  • As transparent as possible for users
  • Algorithm agnostic
  • Works for platform, roaming, syncing and device-bound authenticators

Non-goals

  • Rotating credentials within the same algorithm
  • A composite signature scheme on top of WebAuthn
  • Letting the RP pick between previously agreed keys at sign-in time

The simplest thing that works: every new bit of complexity cuts across RPs, user agents, OS APIs, passkey providers and security keys.

Goals are visible from the start. Emphasize: no lock-out, extensions keep working, works everywhere.
Non-goals: no rotation within the same algorithm, no composite signatures, no RP-selected keys at sign-in time.
We want the simplest solution, since complexity cuts across every layer of the ecosystem.

Part 1 · Backing up & restoring credentials

Stateless credentials

  • Stateless credentials already behave this way, for every credential ever issued.
  • But the authenticator can't know which ones it issued, so existingCredentials is [].
  • That's fine: the only way to get an assertion for a stateless credential is an allow-list anyway.
Stateless (non-resident) credentials can always be used again if the RP names them, so they are already "restorable".
The authenticator can't enumerate them, so it reports an empty list.
And they're only reachable via an allow-list, so the RP doesn't need the list.

The upgrade happens inside the sign-in

Part 2 · The algUpgrade extension

IDL & processing

dictionary AuthenticationExtensionsAlgUpgradeInputs {
  // Parameters for the new credential.
  required sequence<PublicKeyCredentialParameters> pubKeyCredParams;
};

dictionary AuthenticationExtensionsAlgUpgradeOutputs {
  // Make credential authenticator data.
  ArrayBuffer authenticatorData;
};

// Signed extension outputs.
$$extensionOutput //= (
  algUpgrade: {
    authData: bstr,
  }
)
  • Pick the first alg in pubKeyCredParams the authenticator supports.
  • Already has a credential with that alg for this user + RP? Normal assertion.
  • Otherwise mint one. The old credential signs the assertion, which carries the new authData.
  • Only authenticators that support restoring credentials may expose it.

Alternative: sign a hash of the authData, or of credential ID + COSE key. Is the extra complexity warranted?

The extension has a single input: the list of acceptable algorithms, in order of preference.
The authenticator walks pubKeyCredParams and picks the first algorithm it supports.
If it already has a credential for that algorithm, this is just a normal assertion. That makes the request idempotent.
Otherwise it creates a new credential and returns its authenticator data inside the signed extension outputs of the old credential. That's the transfer of trust.
algUpgrade depends on restore: only authenticators that keep backups can expose it.
Footnote from the explainer: we could sign a hash instead of the whole authData. Not obviously worth it.

Part 2 · The algUpgrade extension

What carries over

Part 2 · The algUpgrade extension

Credential Manager Trust Group keys

CMTG keys use the same algorithm as the credential's private key.

cmtgKey ⟶ cmtgKeys: [ ECDSA ML-DSA ]
  • Return a list of keys instead of a single key (w3c/webauthn#2472).
  • No eligible key uses the new algorithm? Mint one and return it alongside the existing key, transferring trust.
  • A lost CMTG key is not a lock-out (RPs already handle new trust groups), so the old-algorithm key can be dropped right away.
CMTG keys are specified to be the same algorithm as the private key, so they need to be upgraded too.
Today an assertion can return a single CMTG key. We should change that to a list (issue 2472).
If none of the eligible keys uses the selected algorithm, mint a new key and return it next to the old one.
Unlike passkeys, losing a new CMTG key in transit doesn't lock anyone out, so authenticators can drop the old key immediately.

Part 3 · The relying party's view

RP integration

// client.js: accounts/signin
const assertion = await navigator.credentials.get({
  publicKey: {
    …,
    extensions: {
      algUpgrade: {
        pubKeyCredParams: [
          { alg: -48, type: 'public-key' },  // ML-DSA-44
          { alg: -7, type: 'public-key' },   // ECDSA
        ],
      },
    },
  },
});
fetch('webauthn/assert', { method: 'POST', body: … });
// server.js: webauthn/assert

// [Validate the assertion.]

let ext = parseExtensions(
    assertion.response.authenticatorData);
let newCredential = ext.algUpgrade?.authenticatorData;
if (newCredential) {
  // [Replace the user's credential.]
}

// [Continue with sign in as normal.]

Switching to a new algorithm = editing pubKeyCredParams.

From the RP's side, this is a small change to an existing sign-in.
Pass the accepted algorithms, sorted by preference, on get() requests.
On the server, validate the assertion as usual.
If there's a new credential in algUpgrade, replace the stored credential with it.
To move to another algorithm later, just update the list.

Wrap-up

Discussion

  • Sign the new credential's full authData, or a hash of it (or of credential ID + COSE key)?
  • Should restoring on allow-list requests be unconditional for capable authenticators, independent of the extension?
  • CMTG: return a list of keys instead of a single key (#2472)?
  • Usernameless recovery costs a second ceremony. Acceptable, given the alternatives?
Questions for the group.
Signed output: the full authData is simplest. A hash is smaller but adds complexity.
The explainer proposes that restore-on-allow-list always applies for supporting authenticators, even without the extension.
CMTG keys: single key to a list, issue 2472.
Usernameless recovery needs two ceremonies. Alternatives that avoid it have worse trade-offs.
