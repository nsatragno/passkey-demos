Requirements

  • One ceremony
  • Same authenticator
  • Recoverable
  • Algorithm agnostic
So, from the last two slides: what does a real solution need?
One ceremony: no second prompt. The upgrade rides along an ordinary get().
Same authenticator: the new credential must be created where the existing one lives.
Recoverable: if the response never reaches the server, the user isn't locked out.
Algorithm agnostic: nothing is specific to ML-DSA. The same mechanism moves credentials to whatever algorithm comes next.

Where this goes from here: four next steps.
The first piece is already up for review: w3c/webauthn#2475. It changes the authenticator model so a create that would overwrite a credential appends it to a list instead. Empty allow-lists return the newest; allow-lists return the newest match and erase the rest. Existing authenticators count as having one slot, so nothing changes for them. The Signal API is updated to work on the list. Please review!
Then a public prototype built on top of the virtual authenticator, so RPs and implementers can try the whole flow before anything ships.
Next, follow-up WebAuthn changes to standardize both extensions we just saw: restoreCredentials and algUpgrade.
And CTAP needs to catch up: security keys need to learn the new model, where they can store multiple credentials per RP ID and user ID, and the credential management API needs updating to match. Authenticators also need to advertise the capability.

Feature detection

// Does the browser support the extensions?
const caps =
    await PublicKeyCredential.getClientCapabilities();
caps['extension:algUpgrade'];          // true / false
caps['extension:restoreCredentials'];  // true / false

// Authenticator support: just ask.
const assertion = await navigator.credentials.get({
  publicKey: {
    challenge,
    extensions: {
      algUpgrade: { pubKeyCredParams },
    },
  },
});
// algUpgrade output present ⇒ upgraded
  • Browser: getClientCapabilities() reports whether it can relay the extensions.
  • Authenticator: only known per request. Always send algUpgrade: capable authenticators return a new credential, others don't.
  • Safe by default: unknown extensions are ignored, so sending it never breaks sign-in.
How does an RP know whether this will work? Nothing new is needed: WebAuthn already standardizes extension feature detection.
getClientCapabilities() already reports a key "extension:<id>" for every extension the client implements. If it isn't true, the RP may assume the client won't process or forward it.
The authenticator side can't be known up front, and that's fine: the RP keeps sending algUpgrade on every sign-in and gets a new credential once the user's authenticator supports it.
Like any extension, it's ignored by clients and authenticators that don't understand it, so there's no breakage and no need to target users.

RP integration

// client.js: accounts/signin
const assertion = await navigator.credentials.get({
  publicKey: {
    …,
    extensions: {
      algUpgrade: {
        pubKeyCredParams: [
          { alg: -48, type: 'public-key' },  // ML-DSA-44
          { alg: -7, type: 'public-key' },   // ECDSA
        ],
      },
    },
  },
});
fetch('webauthn/assert', { method: 'POST', body: … });
// server.js: webauthn/assert

// [Validate the assertion.]

let ext = parseExtensions(
    assertion.response.authenticatorData);
let newCredential = ext.algUpgrade?.authenticatorData;
if (newCredential) {
  // [Replace the user's credential.]
}

// [Continue with sign in as normal.]

Switching to a new algorithm = editing pubKeyCredParams.

From the RP's side, this is a small change to an existing sign-in.
Pass the accepted algorithms, sorted by preference, on get() requests.
On the server, validate the assertion as usual.
If there's a new credential in algUpgrade, replace the stored credential with it.
To move to another algorithm later, just update the list.
