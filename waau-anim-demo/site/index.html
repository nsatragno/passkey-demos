WebAuthn · Post-quantum migration

Upgrading passkeys to post‑quantum, one sign‑in at a time

A visual walkthrough of the Web Authentication Algorithm Upgrades proposal: how a relying party can swap the key inside a credential the user already has for a post-quantum one, without asking anyone to re-register, and how to recover when an upgrade gets lost on the way.

Chapter 1

The problem

Every credential WebAuthn has ever produced uses a classical signature algorithm. That's billions of passkeys synced by passkey providers, and billions more bound to the hardware of security keys. A cryptographically relevant quantum computer would make all of those signatures forgeable.

Credentials can't just be re-issued in bulk: each one belongs to one user, one relying party, and often one piece of hardware. The proposal sets out these goals:

  • Relying parties get a way to migrate credentials from one algorithm to another.
  • It works for both kinds of authenticators: passkey providers, which store credentials in software and sync them, and security keys, which bind credentials to dedicated hardware.
  • A partial, failed migration can be recovered.
  • Extensions keep working after the migration.
  • It is as transparent to users as possible.

Out of scope Rotating keys within the same algorithm, composite signatures layered on top of WebAuthn, and letting the RP choose between several pre-agreed keys at sign-in. Any new complexity touches every layer of the ecosystem (RPs, browsers, OS APIs, passkey providers, security keys), so the guiding principle is: the simplest design that meets the goals.

Chapter 2

Why not just get(), then create()?

A relying party can already sign the user in and then immediately ask for a new credential with a post-quantum algorithm. Watch what goes wrong:

The proposal splits the problem into two independent capabilities, which can be built in parallel:

  1. 1
    Backups. When a new credential replaces an old one, the authenticator keeps the old one around, and the RP can tell when it needs to fall back to it.
  2. 2
    Upgrade-in-assertion. The RP can ask for a new credential as part of a sign-in, so the old key vouches for the new one.

Chapter 3 · Capability 1

From one slot to a list

WebAuthn models an authenticator as a credentials map keyed by { user id, RP ID }. One key, one credential. That makes replacing a credential risky:

The proposal changes the model so that { user id, RP ID } maps to a list of credentials sorted by creation time. New credentials are appended, and requests with an empty allow-list always return the newest one.

Prior art Google Password Manager already does a version of this: it keeps shadowed credentials that still answer allow-list requests. That behaviour isn't standard, though, and RPs have no way to reach those credentials from an empty allow-list request. The proposal standardizes a variant of it.

Chapter 4 · Capability 1

The cleanup rule

Backups can't pile up forever, and stale ones shouldn't come back. One rule handles both: an allow-list request tells the authenticator which credential the RP actually knows about.

  • On an allow-list request, the authenticator uses the newest credential that matches and erases every other credential for that { user id, RP ID }.
  • This applies whenever the authenticator supports it, whether or not the RP requested the extension.
  • Authenticators may also delete old credentials when they need room for new ones.

A new assertion extension reports the backups, so the RP can tell what happened:

partial dictionary AuthenticationExtensionsClientInputs {
  boolean restoreCredentials;
};

dictionary RestoreCredentialsOutput {
  sequence<ArrayBuffer> existingCredentials;
};

// Signed extension outputs.
$$extensionOutput //= (
  restoreCredentials: { existingCredentials: [* bstr] }
)
Edge cases: stateless credentials, excludeCredentials, and the Signal API

Stateless credentials (where the credential ID wraps the key) already behave this way: every credential ever issued keeps working. But the authenticator can't list them, so existingCredentials is []. That's fine, because a stateless credential can only be asserted through an allow-list anyway.

excludeCredentials: an authenticator is excluded if any of its credentials matches the list, backups included.

Signal API: for backwards compatibility, signals that refer to the newest credential act on the whole list as if it were one credential.

MethodNew behaviour
signalCurrentUserDetailsUpdates every credential, shadowed ones included.
signalUnknownCredentialIf the ID is the newest credential, the whole list is hidden or erased. If it's a backup, nothing happens (that indicates an RP or authenticator bug).
signalAllAcceptedCredentialsA second way to recover: the newest credential that's on the list is kept (and un-hidden if needed) and every other credential is erased. If nothing matches, all of the user's credentials are hidden or erased.

Chapter 5 · Capability 2

The upgrade happens inside the sign-in

With backups in place, here's the main event. The RP adds an algUpgrade extension to an ordinary navigator.credentials.get() call, listing the algorithms it accepts in order of preference.

The authenticator picks the first algorithm in pubKeyCredParams it supports. Then:

  • If it already holds a credential with that algorithm for this user and RP, it returns a normal assertion. Nothing changes.
  • Otherwise it mints a new credential, builds its make-credential authenticatorData, and returns a normal assertion signed by the old credential, with the new authenticatorData inside the signed extension outputs.

Because the new credential's data is covered by the old signature, trust transfers from A to B. Only authenticators that support backups may offer this extension, so a lost upgrade can always be recovered.

dictionary AuthenticationExtensionsAlgUpgradeInputs {
  // Parameters for the new credential.
  required sequence<PublicKeyCredentialParameters> pubKeyCredParams;
};

dictionary AuthenticationExtensionsAlgUpgradeOutputs {
  // Make credential authenticator data.
  ArrayBuffer authenticatorData;
};

The RP side is small. To move to a new algorithm, the RP edits pubKeyCredParams:

// client.js: accounts/signin
const assertion = await navigator.credentials.get({ publicKey: {
  ...,
  extensions: {
    algUpgrade: {
      pubKeyCredParams: [
        { alg: -48, type: 'public-key' },  // ML-DSA-44
        { alg: -7,  type: 'public-key' },  // ECDSA
      ],
    },
  },
}});

// server.js: webauthn/assert
// [Validate the assertion as usual.]
const ext = parseExtensions(assertion.response.authenticatorData);
const newCredential = ext.algUpgrade?.authenticatorData;
if (newCredential) {
  // [Replace the user's credential with the new one.]
}
// [Continue with sign in as normal.]

Chapter 6

When the upgrade gets lost

The risky moment is after the authenticator has minted B and before the server has saved it. Connections drop, tabs close, servers time out. What happens next depends on whether the RP uses allow-lists.

Allow-list flows recover on their own

bank.com uses security keys as a second factor, so every request carries an allow-list.

Usernameless flows need one extra round trip

shrine.com uses passkeys as a first factor with empty allow-lists. The authenticator returns the newest credential, B, which the server has never seen. This is where existingCredentials comes in.

existingCredentials lets the RP tell apart two situations that otherwise look the same: "the user deleted this passkey on our account page" and "an upgrade never reached us". Recovery costs a second ceremony, but only on this rare failure path. Every alternative that avoids it has worse trade-offs (see chapter 10).

Dogfooding In empty allow-list flows the RP can't choose which users get upgraded, because the request goes out before it knows who the user is. A workable approach is a cookie that marks devices as eligible for the upgrade.

Chapter 7

What carries over to the new credential

A credential is more than a key pair. RPs rely on PRF outputs to decrypt data, on large blobs, on credProtect levels. If any of these changed during an upgrade, the upgrade would break something.

PRF & hmac-secret

Copied, so PRF outputs stay identical. Data the RP encrypted with them stays decryptable.

largeBlob

Copied after any large blob write in the same request. On security keys, the simplest approach is to copy the largeBlobKey.

credBlob

Set once at creation and can't be changed, so it's copied.

credProtect & third-party payment

Copied as-is.

CMTG keys

A CMTG key uses the same algorithm as the credential, so assertions will return a list of keys. If none uses the new algorithm, a new CMTG key is minted and returned next to the old one. Once it has been returned, the old CMTG key can be dropped.

Nothing to do

credProps, appId/appIdExclude (U2F devices are not eligible), remoteClientDataJson, minPinLength, pinComplexityPolicy.

No attestation Credentials created this way can't carry an attestation statement. They don't need one: if the RP trusted the original credential's attestation, it can trust a credential that the original signed. For the same reason, new credentials can't output creation-time extensions. An upgrade can't give a credential capabilities the original didn't have.

Chapter 8

Security keys don't have screens

For passkey providers like Google Password Manager, the change is small: shadowed credentials already exist, and minting a new credential right before returning an assertion is easy. Hardware security keys are more constrained.

CTAP gets a mirror of the extension that only runs when a request resolves to exactly one credential. It's proposed to be mandatory in the next CTAP version, along with backups.

Storage, batching, and memory constraints

Storage. Keeping backups takes extra space. One way to save it: store a single large source of entropy per (user, RP) and a small random suffix per credential, with credential IDs pointing at an entropy + suffix pair. The suffix accounts for ML-DSA's rejection sampling (not every random sample is a valid key) and avoids always rotating to the same key.

Allow-list batching. Platforms probe allow-lists with the UP bit set to zero to narrow them down. If an RP sends several IDs for the same user and authenticator, such a probe could erase the newer credential instead of the older one. The options are to have UP=0 requests skip erasing, or to require that RPs never send more than one ID per user and authenticator.

Working memory. If returning a new credential and an assertion from a single command turns out to be too much for small chips, the command can be split into two, with the extension output carrying a hash of the new authenticatorData instead of the full data.

Full storage. A nearly full key might delete a backup before the RP gets a chance to restore it. That takes several rare events at once, but RPs may run into it.

Chapter 9

Upgrade while the old keys are still trusted

Recovery has a quiet assumption built in: when the RP falls back to credential A, it's trusting a classical signature.

Once quantum computers are practical, an assertion from an unknown credential that falls back to a classical key could be an attacker trying to downgrade the RP. At that point the safe move is to treat the user as never upgraded and step them up with another authentication method. The API doesn't decide which algorithms an RP should trust. That's up to the RP.

User handles The design (like the Signal API) assumes each user has a single, unique user handle, as the spec requires ("It is RECOMMENDED to let the user handle be 64 random bytes"). RPs that reuse handles across users are already broken and are explicitly not supported.

Chapter 10

Roads not taken

The main competing proposal is Microsoft's algPolicy. It keeps credentials of every algorithm side by side, as insurance in case a new algorithm is broken.

The proposal's position is that this insurance is better provided by hybrid signature schemes, which are simpler and also guard against unknown weaknesses in new algorithms. It keeps the protocol small.

Send the new public key on every assertion

The authenticator would attach B's public key, signed by A, to every response, so a lost upgrade fixes itself without a second ceremony.

Why not: it makes every assertion bigger and slower to help a tiny fraction of them (about 1 in 70 google.com assertions go unrecognised, and that's a generous upper bound). It also still needs the allow-list cleanup, and the authenticator never learns that a backup was used.

Client-only extension

The browser does a get and then a create by itself, so even today's security keys could work.

Why not: there's no transfer of trust, PRF secrets can't be preserved, existing keys need two taps, and stateful credentials on current keys could be lost.

Multiple key slots per credential

One credential ID holds several keys of different algorithms, and assertions return all of the signatures.

Why not: it's unclear how it would work for stateless credentials, it breaks on platforms that don't know about the extension, and authenticators would need both single-key and multi-key modes.

Two-step upgrade

Like conditional create: after a sign-in, the RP calls create() and the browser silently mints a credential.

Why not: the RP could target specific users, but it can't work for NFC security keys, since nobody holds a key to the reader during a network round trip.

Rely on the Signal API for cleanup

Let signalAllAcceptedCredentials decide when backups are deleted, instead of the authenticator.

Why not: no platform supports signals for security keys, NFC keys are gone by the time the signal arrives, and RPs that never call it leave orphaned credentials.

Just a supported flag

An earlier, simpler version of restoreCredentials that only reported support.

Why not: the RP couldn't tell "deleted by the user" from "lost upgrade" without tracking deleted credentials, or know whether this authenticator had a backup.

Chapter 11

Recap

  1. Authenticators keep a list of credentials per { user id, RP ID }, newest first for discoverable requests.
  2. Allow-lists clean up: the newest matching credential wins, and every other credential is erased.
  3. restoreCredentials reports the backup IDs, so RPs can tell a lost upgrade from a deleted passkey.
  4. algUpgrade mints a credential with the RP's preferred algorithm during a normal assertion, and the old key signs over the new one.
  5. Extension state is copied, so PRF, large blob, credBlob, credProtect and payment all keep working.
  6. Security keys only upgrade a single, user-selected credential, using credential enumeration for usernameless flows.
  7. Start early, while classical algorithms can still be trusted for recovery.

Shipping it The WebAuthn virtual authenticator gains a supportsRestoringCredentials option and an algUpgrade parameter, both shown in DevTools. Chrome will record a kWebAuthnAlgUpgradeExtension use counter and histograms measuring how many security keys support the extension. The extension is opt-in for websites and rolls out through the regular waterfall process.
